# Password Reset

A forgotten credential can't be used to prove who you are, so recovery leans on
something the account holder *holds*. **Email is deliberately not a channel** — an
inbox proves nothing about who controls a wallet. There are exactly two anchors:

| Channel | Who | How you prove it | What it resets |
|---------|-----|------------------|----------------|
| `ussd` | Anyone with a phone | Dial `*715*…#` **from the SIM** on the account | Password only |
| `portal` | Students | A 6-digit code lands in your **school portal** notification bell | PIN (sign-in **and** payment) |

`/start` picks the channel for you from the account. You don't choose it.

## Why the two channels reset different things

This is the important part of the design, not an implementation detail.

**Phone (`ussd`)** proves possession of the SIM. Dialing *originates* the USSD
session, which only the person holding that SIM can do — there's no SMS to
intercept, and it works where SL SMS delivery doesn't. But a SIM can be stolen. So
this channel **never writes `transaction_pin`**: the thief recovers the login and
still cannot move money, because every payment re-checks the PIN.

**School portal (`portal`)** proves control of the student's portal login on
`gov.school.edu.sl`. Peeap asks the school to drop a code into that student's own
notification bell; the school generates, holds and verifies it — **Peeap never sees
the code**, it only asks *"is this code valid for this NSI?"*. For students the PIN
*is* the sign-in credential (`password_hash = bcrypt(pin)`), so this channel resets
**both**. That's safe precisely because the anchor is the school portal, which
someone holding a stolen SIM has no way to reach.

<Note>
A student who forgot their PIN recovers through the portal, not the phone — even if
they have a phone on file. Sending them down the SIM path would restore login but
leave the forgotten payment PIN in place, which is a half-recovery.
</Note>

## How it works

<Steps>
  <Step title="Start the reset">
    Submit the phone, email, or NSI the user signs in with. The response tells you
    which `channel` was chosen — and for `ussd`, the `dialCode` to display.
  </Step>
  <Step title="They prove the anchor">
    `ussd`: they dial `*715*…#`; poll `/status` until it flips to `verified`.
    `portal`: they read the code in their school portal and POST it to `/verify`.
    Either way you get a one-time `resetToken`.
  </Step>
  <Step title="Set the new secret">
    Spend the token. `ussd` sends `password`; `portal` sends `pin`. Every existing
    session is revoked, so anyone already signed in is evicted.
  </Step>
</Steps>

## Start a reset

`POST /auth/forgot-password/start`

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `identifier` | string | Yes | Phone, email, or student NSI — whatever the user signs in with |

### Example Request

```bash
curl -X POST https://api.peeap.com/auth/forgot-password/start \
  -H "Content-Type: application/json" \
  -d '{ "identifier": "076000000" }'
```

### Success Response (200)

Phone account — show the `dialCode`:

```json
{
  "resetId": "3f9c1a7e-2b44-4c8d-9e11-5a7b3c2d1e00",
  "channel": "ussd",
  "dialCode": "*715*025748#",
  "maskedTarget": "076***000",
  "expireTime": "2026-07-13T11:45:43Z"
}
```

Student — the code is already in their portal; there is nothing to display:

```json
{
  "resetId": "3f9c1a7e-2b44-4c8d-9e11-5a7b3c2d1e00",
  "channel": "portal",
  "maskedTarget": "your school portal",
  "expireTime": "2026-07-13T11:45:43Z"
}
```

<TryIt method="POST" url="/auth/forgot-password/start" body={`{ "identifier": "076000000" }`} />

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `identifier_required` | No identifier supplied |
| 404 | `account_not_found` | No account matches those details |
| 409 | `no_recovery_channel` | Account has no phone and no student record — needs support |
| 429 | — | Rate limited (3/hr per account, 10/hr per IP) |
| 502 | `otp_send_failed` | The school portal couldn't be reached |
| 502 | `reset_unavailable` | Provider temporarily unavailable |

<Note>
The limits are tighter than login's: every USSD session costs money and dials a real
handset.
</Note>

## Poll the status — `ussd` only

`GET /auth/forgot-password/status?id={resetId}`

Poll every few seconds while the user dials. The moment it flips to `verified`, the
response carries a **one-time `resetToken`** — capture it, because it is returned
exactly once and is never recoverable afterwards.

### Example Request

```bash
curl "https://api.peeap.com/auth/forgot-password/status?id=RESET_ID"
```

### Responses (200)

```json
{ "status": "pending" }
```

```json
{
  "status": "verified",
  "resetToken": "b7f3…",
  "expiresInSeconds": 600
}
```

```json
{ "status": "expired" }
```

<TryIt method="GET" url="/auth/forgot-password/status?id=RESET_ID" />

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `wrong_channel` | This is a `portal` session — use `/verify` |
| 404 | `not_found` | Unknown `resetId` |
| 409 | `already_used` | The reset was already completed |

## Verify the code — `portal` only

`POST /auth/forgot-password/verify`

The student reads the code in their school portal notification bell and submits it.
Peeap forwards it to the school and asks whether it's valid for that NSI — the code
is never stored on our side. The school enforces one-shot use, a 5-attempt cap and a
5-minute TTL; we rate-limit guesses per NSI on top, so a fresh session can't buy an
attacker a clean slate.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `resetId` | string | Yes | The `resetId` from Start a reset |
| `code` | string | Yes | The 6-digit code from the school portal |

### Example Request

```bash
curl -X POST https://api.peeap.com/auth/forgot-password/verify \
  -H "Content-Type: application/json" \
  -d '{ "resetId": "RESET_ID", "code": "123456" }'
```

### Success Response (200)

```json
{
  "status": "verified",
  "resetToken": "b7f3…",
  "expiresInSeconds": 600
}
```

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `wrong_channel` | This is a `ussd` session — poll `/status` instead |
| 401 | `invalid_code` | Wrong code — may include `attemptsRemaining` |
| 410 | `expired` | The code expired |
| 429 | — | Too many wrong codes |

## Set the new secret

`POST /auth/forgot-password/reset`

Spends the `resetToken`. **Which field you send depends on the channel** — and the
server enforces which one it will honour, so a `ussd` session cannot set a PIN no
matter what it posts.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `resetId` | string | Yes | The `resetId` from Start a reset |
| `resetToken` | string | Yes | The one-time token from `/status` or `/verify` |
| `password` | string | `ussd` | New password — minimum 8 characters |
| `pin` | string | `portal` | New PIN — 4 to 6 digits |

### Example Request

```bash
# ussd channel
curl -X POST https://api.peeap.com/auth/forgot-password/reset \
  -H "Content-Type: application/json" \
  -d '{ "resetId": "RESET_ID", "resetToken": "RESET_TOKEN", "password": "my-new-password" }'

# portal channel (student)
curl -X POST https://api.peeap.com/auth/forgot-password/reset \
  -H "Content-Type: application/json" \
  -d '{ "resetId": "RESET_ID", "resetToken": "RESET_TOKEN", "pin": "4821" }'
```

### Success Response (200)

```json
{ "success": true, "channel": "ussd", "message": "Password updated. You can now sign in." }
```

The account holder is emailed and notified in-app, and the message states exactly
what changed — a student is told their PIN now covers sign-in *and* payments; a
phone user is told their payment PIN was **not** touched.

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `weak_password` | Shorter than 8 characters (`ussd`) |
| 400 | `invalid_pin` | Not 4–6 digits (`portal`) |
| 403 | `not_verified` | The challenge hasn't been passed yet |
| 403 | `invalid_token` | Bad `resetToken` |
| 409 | `already_used` | The token was already spent |
| 410 | `expired` | More than 10 minutes since verification |

## Security notes

- **Possession, not knowledge.** Both channels prove you hold something — a SIM, or a
  school portal login. A leaked password database gets an attacker nowhere.
- **The PIN boundary is enforced server-side.** Only the `portal` channel may write
  `transaction_pin`. A `ussd` session that posts a `pin` field is simply ignored.
- **Peeap never sees the portal code.** It's generated, delivered and verified by the
  school. We only ask whether it was valid.
- **Single-use, short-lived.** The `resetToken` is random, stored only as a SHA-256
  hash, valid 10 minutes, and burned atomically — a race between two requests can
  only ever set one credential.
- **Sessions are revoked.** An attacker who was already signed in is thrown out the
  moment the real owner recovers the account.
