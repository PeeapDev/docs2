# Password Reset

A forgotten password can't be used to prove who you are, so Peeap proves the **SIM**
instead. We return a USSD dial code; the user dials it **from the number on the
account**. Dialing *originates* the USSD session, which only the person holding
that SIM can do. There's no SMS, so recovery still works where SMS delivery
doesn't. Accounts with no phone on file fall back to a 6-digit emailed code.

This reuses the same dial-to-verify primitive as the
[Verify API](/api-reference/verify/create), pointed at recovery.

<Note>
A reset restores **login only**. The `transaction_pin` that authorizes payments is
never written by this flow — so someone who steals a SIM can take the account but
still cannot move money out of the wallet.
</Note>

## How it works

<Steps>
  <Step title="Start the reset">
    Submit the phone, email, or student ID the user signs in with. You get back a
    `resetId` and — for phone accounts — a `dialCode`.
  </Step>
  <Step title="The user proves the SIM">
    They dial `*715*…#` from the number on the account. Poll
    `/auth/forgot-password/status` until it flips to `verified`, which hands you a
    one-time `resetToken`.
  </Step>
  <Step title="Set the new password">
    Exchange the `resetToken` for a password change. Every existing session is
    revoked, so anyone already signed in is evicted.
  </Step>
</Steps>

## Start a reset

`POST /auth/forgot-password/start`

Resolves the identifier to an account and opens a challenge on the best available
channel: `ussd` if the account has a phone, otherwise `email`.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `identifier` | string | Yes | Phone, email, or student NSI — whatever the user signs in with |

### Example Request

```bash
curl -X POST https://api.peeap.com/auth/forgot-password/start \
  -H "Content-Type: application/json" \
  -d '{ "identifier": "076000000" }'
```

### Success Response (200)

Phone account — show the `dialCode` and ask the user to dial it:

```json
{
  "resetId": "3f9c1a7e-2b44-4c8d-9e11-5a7b3c2d1e00",
  "channel": "ussd",
  "dialCode": "*715*025748#",
  "maskedTarget": "076***000",
  "expireTime": "2026-07-13T11:45:43Z"
}
```

Account with no phone — a 6-digit code is emailed instead:

```json
{
  "resetId": "3f9c1a7e-2b44-4c8d-9e11-5a7b3c2d1e00",
  "channel": "email",
  "maskedTarget": "mo****d@example.com",
  "expireTime": "2026-07-13T11:55:43Z"
}
```

`maskedTarget` is safe to render — it's enough for a user to recognise their own
number or address, not enough to learn someone else's.

<TryIt method="POST" url="/auth/forgot-password/start" body={`{ "identifier": "076000000" }`} />

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `identifier_required` | No identifier supplied |
| 404 | `account_not_found` | No account matches those details |
| 409 | `no_recovery_channel` | Account has neither phone nor email — needs support |
| 429 | — | Rate limited (3/hr per account, 10/hr per IP) |
| 502 | `reset_unavailable` | Provider temporarily unavailable |

<Note>
The limits are deliberately tighter than login's: every USSD session costs money
and dials a real handset.
</Note>

## Poll the status (USSD channel)

`GET /auth/forgot-password/status?id={resetId}`

Poll every few seconds while the user dials. The moment the session flips to
`verified`, the response carries a **one-time `resetToken`** — capture it, because
it is returned exactly once and is never recoverable afterwards.

### Query Parameters

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | Yes | The `resetId` from Start a reset |

### Example Request

```bash
curl "https://api.peeap.com/auth/forgot-password/status?id=RESET_ID"
```

### Responses (200)

Still waiting for the dial:

```json
{ "status": "pending" }
```

Dialed — the SIM is proven:

```json
{
  "status": "verified",
  "resetToken": "b7f3…",
  "expiresInSeconds": 600
}
```

Not dialed in time:

```json
{ "status": "expired" }
```

<TryIt method="GET" url="/auth/forgot-password/status?id=RESET_ID" />

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `wrong_channel` | This session is verified by code, not by dialing |
| 404 | `not_found` | Unknown `resetId` |
| 409 | `already_used` | The reset was already completed |

## Verify the code (email channel)

`POST /auth/forgot-password/verify`

Only for `channel: "email"` sessions. Exchanges the 6-digit code for the same
one-time `resetToken`. Five wrong guesses kill the session.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `resetId` | string | Yes | The `resetId` from Start a reset |
| `code` | string | Yes | The 6-digit code from the email |

### Example Request

```bash
curl -X POST https://api.peeap.com/auth/forgot-password/verify \
  -H "Content-Type: application/json" \
  -d '{ "resetId": "RESET_ID", "code": "123456" }'
```

### Success Response (200)

```json
{
  "status": "verified",
  "resetToken": "b7f3…",
  "expiresInSeconds": 600
}
```

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 401 | `invalid_code` | Wrong code — response includes `attemptsRemaining` |
| 410 | `expired` | The code expired |
| 429 | `too_many_attempts` | Five wrong guesses; start again |

## Set the new password

`POST /auth/forgot-password/reset`

Spends the `resetToken` and writes the new password. The token is single-use, and
completing a reset **revokes every existing session** on the account.

### Request Body

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `resetId` | string | Yes | The `resetId` from Start a reset |
| `resetToken` | string | Yes | The one-time token from status/verify |
| `password` | string | Yes | The new password — minimum 8 characters |

### Example Request

```bash
curl -X POST https://api.peeap.com/auth/forgot-password/reset \
  -H "Content-Type: application/json" \
  -d '{
    "resetId": "RESET_ID",
    "resetToken": "RESET_TOKEN",
    "password": "my-new-password"
  }'
```

### Success Response (200)

```json
{ "success": true, "message": "Password updated. You can now sign in." }
```

The account holder is emailed and notified in-app that the password changed — if
it wasn't them, that's the signal that brings them to support.

### Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `weak_password` | Shorter than 8 characters |
| 403 | `not_verified` | The SIM/code challenge hasn't been passed yet |
| 403 | `invalid_token` | Bad `resetToken` |
| 409 | `already_used` | The token was already spent |
| 410 | `expired` | More than 10 minutes since verification |

## Security notes

- **Possession, not knowledge.** The dial proves the SIM is physically in hand. A
  leaked password database, or a known phone number on its own, gets an attacker nowhere.
- **The PIN is out of scope.** `transaction_pin` is never written here. Login is
  recoverable from the SIM; spending is not.
- **Single-use, short-lived.** The `resetToken` is random, stored only as a SHA-256
  hash, valid for 10 minutes, and burned atomically — a race between two requests
  can only ever set one password.
- **Sessions are revoked.** An attacker who was already signed in is thrown out the
  moment the real owner recovers the account.
